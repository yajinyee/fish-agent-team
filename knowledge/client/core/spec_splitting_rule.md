# 大型 Spec 拆分規則

## 核心原則

在產出 tasks.md 之前，先判斷整體規模。如果預估 tasks 超過 10 個，或涉及多個可獨立開發的子系統，必須先暫停並主動詢問使用者是否需要拆分為多個獨立子模組 spec。

拆不拆、怎麼拆，由使用者決定。

## 詢問時機

在完成 requirements 和 design 之後、產出 tasks 之前，主動向使用者提出：
- 這個功能規模較大，建議拆分
- 提出建議的子模組劃分方式
- 說明各模組間的依賴關係與可平行開發的組合
- 等使用者確認後再執行

## 拆分後的結構

1. requirements 和 design 集中在總索引 spec 目錄下
2. 子模組資料夾放在主規格目錄下，加上數字前綴表示執行順序（如 `01_basic-setup/`、`02_totem/`），不要散落在 specs 根目錄
3. 子模組只需要 tasks.md，頂部用相對路徑引用總設計文件（如 `> 總設計文件：../design.md`）
4. 總索引的 tasks.md 列出所有子模組，每個主 task 下展開對應子模組的子 task 進度
5. 子模組 task 完成時同步更新總索引進度

## 拆分的判斷參考

- 只有確定可以切開來各自獨立開發的項目才可以拆
- 不同的 UI 面板 / 不同的遊戲階段 / 不同的系統模組 → 適合拆分
- 共用資料結構、事件定義、基礎設定 → 抽成「基本設定」模組，其他模組依賴它
- 模組間共用狀態太多、強依賴無法解耦 → 不適合拆分
