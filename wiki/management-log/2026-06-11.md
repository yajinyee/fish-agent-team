9|## 管理日誌｜2026/06/11
10|
11|### 一、Slotverse 交接方式與實際承接
12|
13|原本一開始規劃，是我、賢名、書夢、怡文會先約一個會議，把交接方向討論清楚後，再進行後續交接。但後來實際發展變成各自去找研二成員交接。
14|
15|我有去詢問賢名為什麼會變成這樣，後來才知道是怡文覺得這樣處理就可以。這件事我心裡其實覺得有一點怪，因為如果沒有先把交接架構、責任分工、時間節點和資料範圍講清楚，後續很容易變成大家各自理解，最後交接品質不一致，甚至到真正要接手時才發現有缺口。
16|
17|也因為這樣，今天我跟宣晴交接時，就直接調整做法。我跟她說，六月中後的活動我會開始加入設計與設定，不等到正式交接後才學，而是在他們還在運作時就一起參與。這樣一邊做、一邊問、一邊接，應該會比單純會議交接更有效。宣晴他們也滿樂意讓我加入。
18|
19|目前我也把一些七月要做的事情提前拉進來，直接跟著 Slotverse 團隊一起運作。魚機版本的部分，先開放到 Lv1 就可以遊玩，主要是為後續魚機移植量產先鋪路。
20|
21|這次交接過程中，有發現幾個需要補起來的區塊：
22|
23|* 設計檔案需要交接。
24|* 設定檔案需要交接。
25|* Client 上傳活動流程需要交接。
26|* Server 上傳活動流程需要交接。
27|* 平台部分由我和琮偉承接。
28|* 營運部分由我和佩妮承接。
29|* 產品移植部分，會由我與魚機組羽農、宗承討論後續由我們這邊搬移，並順便處理 Slotverse、金虎爺相關內容。
30|* 虎機移植部分，我已經請柏合協助。柏合會先派技術來了解，後續再判斷實際怎麼運作。
31|
32|目前目標是六月中能上手 Slotverse 營運，七月把移植事項處理到一個可運作的狀態。
33|
34|這件事讓我比較明確感受到，交接不能只看「有沒有人講過」，而是要看「接手的人是否真的能操作」。如果只是各自找人交接，但沒有形成完整清單和共同節奏，風險其實不小。所以我這次選擇直接進到運作現場，趁原本團隊還在跑的時候把東西接起來。
35|
36|今天比較讓我感動的是，我要離開的時候，承諭跟我說：「如果 Slotverse 你想要做什麼，我週六能幫你。」這句話對我來說滿重要的，因為這不是單純幫忙，而是代表他願意在這個交接和後續推動上一起補位。現在這個階段，能有人願意主動多扛一點，真的很難得。

40|### 二、協助研五啟動 Boss 預測模型
41|
42|今天也有跟商用研五曉慧交流，協助他們啟動「魚機專家 - Boss 預測模型」的第一步。
43|
44|這次我主要先跟他們講解我們猴爺的作法，讓他們理解我們是怎麼整理 Boss 預測模型的前置資料，以及怎麼把玩法、機率、規格、美術等面向拆成可討論、可盤點的維度。
45|
46|在了解研五的產品特性後，我發現他們需要比我們多考慮一個重要維度：曝光率。因為他們每個 Boss 腳本的出場率不同，這會直接影響 Boss 被玩家看見與參與的機會，如果沒有納入，模型結果可能會失真。
47|
48|另外，研五在機率特徵上預計會使用：
49|
50|* 均倍
51|* 最大倍數
52|* 最小倍數
53|* SD 值
54|
55|我覺得這樣的特徵設計會比單純用比較粗的分類更精準，模型準確度應該也有機會更高。
56|
57|這次交流我滿喜歡的地方是，不是單純叫大家回去盤點資料，而是坐下來邊聊、邊理解產品、邊確認哪些維度是真的有意義。這種方式比較花時間，但會比較扎實。因為模型前期如果沒有把產品邏輯和資料定義講清楚，後面即使真的開始建模，也很容易做出一個看似有結果，但實務上不好解釋或不好使用的東西。
58|
59|我也有特別提醒研五，前期可以先處理：
60|
61|* 規格
62|* 玩法
63|* 機率
64|
65|數據可以先撈取，美術則可以放到後面再對。原因是美術判斷相對主觀，不一定能很快定義清楚，而且也未必是第一階段影響成效的主要原因。與其一開始就卡在主觀定義，不如先把比較客觀、比較容易量化的內容整理起來。
66|
67|目前預計一週到兩週內再開一次會議確認，實際時間會取決於研五盤點維度與細節討論的進度。
68|
69|這次經驗也再次提醒我，未來如果要協助其他團隊做預測模型，產品端前期的陪跑很重要。不是只把資料丟給數據或模型端，而是要先幫忙把問題、維度、規格與產品邏輯整理到能被模型使用的程度。

73|### 三、這幾天觀察後，週一可以討論的幾個方向
74|
75|這四天觀察下來，我覺得有幾件事情可以在週一好好討論。這些不是單點任務，而是會影響後續部門 AI 發展、知識沉澱與跨組協作的基礎建設。
76|
77|#### 1. 研發製程知識庫建立
78|
79|我覺得研發製程知識庫可以先從各組開始建立，而不是一開始就直接從部門層級做一個很大的知識庫。
80|
81|比較可行的做法是：各組先建立自己的共用知識庫，並且開 API 讓其他團隊或部門層級可以調用。這樣比較貼近實際運作，也比較容易落地。
82|
83|研發製程知識庫可以先涵蓋：
84|
85|* 開發
86|* 維運
87|* 客訴
88|* Code Review
89|
90|各組 PM 應該要有責任推動自己組內的知識整理。部門層級則不一定要一開始就把所有東西收上來重新整理，而是可以透過各組 Agent 或 API 去調用底下知識。這樣知識蒸餾會比直接從上面做一個大而全的知識庫更實際，也比較不會變成形式工程。
91|
92|#### 2. 正式機 DB Read Only 介面服務
93|
94|部門應該要思考建立正式機 DB 的 Read Only 介面服務，讓其他團隊在發展 AI 工具時，可以在安全環境下持續往前做。
95|
96|這是我聽到阿德分享客訴工具後有感而發的。阿德自己也有意識到資料存取需要防範，投影片上也有提出相關疑慮，這點我覺得很好。
97|
98|但這件事可能不只正式機 DB 需要處理，其他資料來源也可能需要類似的 Read Only 服務。目的不是限制大家做 AI，而是讓大家在比較安全、可控的條件下使用資料。
99|
100|數據組目前好像也有提供 BQ 的 Read Only，我覺得這個方向是對的。未來如果部門要鼓勵大家做 AI 工具，就必須同步把資料存取安全的基礎建設補起來。
101|
102|#### 3. Kiro 使用與企業方案
103|
104|Kiro 的使用和教育目前在部門內已經相對普及，可以思考是否再跟 AWS 談企業方案。
105|
106|公司這邊其實也投入不少心力協助推廣與上課，從商務角度來看，應該可以進一步談看看企業帳號或方案。這件事如果談得成，對後續部門推廣 AI 開發工具會比較有幫助，也可以讓使用與管理更一致。
107|
108|#### 4. 部門基礎 AI 課程
109|
110|部門可以整理一套基礎 AI 課程，並建議幹部持續往下推廣。
111|
112|目前大家對 AI 的理解和使用能力差距還是存在。如果只靠少數人自己摸索，推動速度會不穩定。比較實際的做法，是把基礎能力整理成課程，讓各組幹部能帶回去推廣，先把整體 AI 應用能力拉到一個基本水準。
113|
114|這樣對下一次 AI Review 應該也會有比較明顯的影響。不是只看少數亮點，而是讓更多組都能拿出具體應用。
115|
116|#### 5. 將這次 Review 優秀案例整理成教材
117|
118|這次 AI Review 裡面有一些不錯的案例，幹部可以一起票選，挑出適合複製、適合教學的內容，整理成教材後納入金猴爺教材內開始推廣。
119|
120|我覺得這樣做會比單純 Review 完就結束更有價值。好的案例如果沒有被整理，熱度過了就會散掉；但如果能變成教材，就可以延續成部門的共同資產。

124|### 四、今日管理心得
125|
126|今天的重點其實有兩個：一個是交接，一個是知識沉澱。
127|
128|Slotverse 交接這件事讓我感受到，如果交接方式太鬆散，後面一定會有風險。與其等問題發生，不如直接提前進場，在原團隊還在運作時就跟著做。這樣雖然比較累，但比較能真的接起來。
129|
130|研五 Boss 預測模型的交流，則讓我確認一件事：跨團隊協作時，不能只叫對方盤點資料，而是要坐下來一起理解產品。很多關鍵維度不是一開始就會寫在表格裡，而是要透過討論才會浮出來。
131|
132|這幾天看下來，我也覺得部門如果要繼續推 AI，接下來不能只停在工具展示或單點案例。比較需要補的是知識庫、資料安全介面、基礎課程、案例教材，還有各組可以自己運作的 AI 開發基礎。
133|
134|今天比較實際的待辦是：
135|
136|1. 持續跟進 Slotverse 交接，確認設計、設定、Client、Server、平台、營運與移植各區塊都有負責人。
137|2. 六月中前讓自己能實際上手 Slotverse 營運。
138|3. 七月前把移植相關事項推到可運作狀態。
139|4. 跟進研五 Boss 預測模型，一到兩週內再開會確認盤點結果。
140|5. 週一討論研發製程知識庫、Read Only 資料介面、Kiro 企業方案、AI 基礎課程與 Review 案例教材化。
